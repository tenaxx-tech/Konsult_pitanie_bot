# Переход Telegram-бота на Google: подготовленная версия

## Статус

Код подготовлен; Bothost ещё не переключён. Новая версия по умолчанию использует
`NUTRITION_STORAGE=google`, явный `airtable` остаётся только для отката. Нет
автоматического возврата к Airtable при сбое Google.

Сохранение устроено так: SQLite на постоянном диске принимает дневник и отметку
для передачи одной транзакцией. Ответ не ожидает Google. Отдельный поток раз
в30сек отправляет изменённые дни в Google Таблицу и перечитывает результат.
После неопределённого ответа используется та же строка, не append: повтор не
добавляет дубль. Изменение, пришедшее во время передачи, остаётся в очереди.
Google — облачная копия для дальнейших интеграций; SQLite — рабочее хранилище.
Это не хранение исключительно в Google и не двусторонняя синхронизация.
Изменения в таблице вручную не импортируются автоматически в чат.

## Подключение перед запуском

1. Сохранить архив кода и data/ действующего проекта. Не публиковать архив,
   журналы питания или секреты в GitHub. Зафиксировать активную версию.
2. Подтвердить, какой экземпляр принадлежит @konsult_pitanie_bot. Запускать
   только один экземпляр с одним webhook; второй оставить остановленным.
3. Проверить в Bothost постоянный диск/volume для /app/data. Наличие папки
   не доказывает сохранность после пересоздания контейнера. Нужны резервные
   копии SQLite, включая историю диалога и очередь, и проверка восстановления.
4. Создать ОТДЕЛЬНУЮ Google Таблицу для этого экземпляра. Лист BotJournal,
   первая строка: AccountKey | Day | Version | SnapshotJson | UpdatedAt.
   Заранее выделить достаточно строк. Не сортировать, не вставлять/удалять
   строки; номер закреплён в локальной БД. Поля RAW защищают от формул.
   Одна таблица принадлежит одному экземпляру; дубликаты серверов запрещены.
   Личные таблицы ChatGPT жёстко запрещены адаптером.
5. В выбранном Google Cloud проекте включить Sheets API и подготовить
   служебный аккаунт. Дать ему доступ редактора только к отдельной таблице.
   Не выдавать права на весь Диск и не создавать публичную таблицу.
   Создание ключа и расширение доступа выполняются с подтверждением владельца.
6. Ключ JSON разместить через защищённые настройки хостинга отдельным файлом
   вне репозитория. Никогда не передавать ключи в переписке или PR. Переменные:
   GOOGLE_APPLICATION_CREDENTIALS=/путь/к/секретному.json
   GOOGLE_BOT_SPREADSHEET_ID=ID_отдельной_таблицы
   NUTRITION_STORAGE=google
   CHANNEL_DB=/app/data/channels.sqlite3
   NUTRITION_PERSISTENT_STORAGE_CONFIRMED=true
   Существующие TELEGRAM_BOT_TOKEN,TELEGRAM_OWNER_ID,TELEGRAM_WEBHOOK_SECRET
   и настройки модели сохраняются. GOOGLE_APPLICATION_CREDENTIALS не является
   значением ключа — это путь к файлу. Секреты в Docker image не включать.
7. Прежде чем переключаться, отдельно согласовать импорт прежней истории:
   источник (Google дневник или Airtable), даты, ключи, статусы, цели, закрытие
   дней. Сверить контрольные суммы. Автоматического импорта в этой версии нет.
   Без импорта новый локальный дневник пуст; не объявлять его полным историческим
   дневником пользователя. Старые данные не удалять.
8. Выполнить тест на синтетическом отдельном экземпляре: запись→ответ→выгрузка,
   повтор, ошибка Google, перезапуск, сверка факта/плана. Проверить версии и
   устойчивые номера строк. Только затем переключать рабочую ветку Bothost.
9. После подтверждения полного перехода убрать Airtable-секреты из активного
   проекта, сохранив согласованный путь отката без публикации секретов.

## Проверки и границы

Локальные тесты не доказывают наличие Google-доступа, постоянного диска или
исправность реального webhook. Google-интеграция проверяется отдельно.

Текущий HTTP шлюз по-прежнему разрешает только владельца. Хранилище разделяет
account/day, но онбординга, оплаты, семей, ролей и общей регистрации ещё нет.
Дневные цели в этой версии прежние, для владельца; их нельзя выдавать новым
пользователям как персонально рассчитанные. Текущая модель — GigaChat, не OpenAI.
Подключение модели и пользователей — следующие отдельные изменения.

Снимки в BotJournal сохраняют все структурированные порции, цели и версию дня.
История диалога остаётся в channels.sqlite3 и требует резервного копирования;
она пока не экспортируется в Google. Не обещать перенос абсолютно всех данных.
Защита от конфликтов не заменяет контроль одной активной копии и запрет ручной
перестановки строк. При восстановлении БД сохранять id и ревизии, а не создавать
пустую базу поверх занятой таблицы. Конфликт или недоступность оставляют PENDING.

/sync показывает состояние последнего локально подтверждённого экспорта, но не
перепроверяет Google в реальном времени и не импортирует внешние изменения.
