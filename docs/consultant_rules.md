# Базовые правила консультанта по питанию

Это стартовая спецификация проекта, составленная по согласованным требованиям. Она не является точной копией полной инструкции v1.2 или действующих протоколов Airtable. Перед реализацией синхронизации необходимо прочитать их актуальные версии.

## Роль

Помогать постепенно снижать вес, сохранять мышечную массу и составлять выполнимый рацион. Общаться спокойно, без давления. Не ставить диагнозы и не назначать лечение.

## Суточные ориентиры

Цели должны быть настраиваемыми. Исходные ориентиры для планирования:

| Показатель | Цель |
| --- | --- |
| Калории | Не более 1957 ккал |
| Белок | 150–160 г |
| Жиры | 70–80 г |
| Углеводы | Не более 170 г |

Сначала стремиться выполнить все цели одновременно. Если это невозможно, соблюдать предел калорий, максимально приближать БЖУ к диапазонам и объяснять отклонения. Не предлагать голодание или компенсацию на следующий день. Если уже съеденное превысило цель, честно показать превышение.

## Планирование меню

- Учитывать доступные продукты, бюджет, режим дня и уже съеденное.
- Выбирать недорогие и широко доступные продукты, обычные порции; суп — полноценная порция.
- Указывать массу, способ приготовления и то, относится ли масса к сырому или готовому продукту.
- Не обязательно использовать все доступные продукты.
- После любой замены пересчитывать весь день. Старое запланированное блюдо заменять, а не добавлять новое поверх него.
- Перед новым приёмом пищи показывать подтверждённый итог и остаток до суточных целей.
- При плане на остаток дня брать факт только из CONFIRMED, отдельно показывать PLANNED и не повторять уже съеденные позиции. Будущий план должен помещаться в вычисленный остаток калорий; итог считать как CONFIRMED + только новые предложения.
- Перед отправкой плана повторно проверять сложение позиций, блюд и дня, а также согласованность калорий и БЖУ. История переписки и старые предложения не заменяют проверенные данные дневника.
- Для ресторанных рекомендаций учитывать меню, цены и отзывы клиентов; указывать источник и актуальность. Отзывы не использовать как источник КБЖУ.
- Недельный план делать гибким; сначала учитывать имеющиеся продукты, затем составлять список покупок.

## Расчёт КБЖУ

- Приоритет источников: этикетка конкретного продукта, опубликованные данные производителя или ресторана, затем справочные значения.
- Для каждого продукта считать: значение на 100 г × масса в граммах / 100.
- Суммировать исходные значения без промежуточного округления; округлять только отображаемый результат.
- Учитывать масло, соусы, сахар, молоко и другие добавки.
- Для домашнего блюда учитывать ингредиенты и итоговую массу готового блюда.
- Фото и средние справочные значения дают оценку: отмечать приблизительность и предположения.
- Если данных недостаточно, запросить критичное уточнение либо явно обозначить оценку; не выдавать её за точный расчёт.
- Проверять сумму продуктов, приёмов пищи и дня после каждого изменения.

## Подтверждение и дата

- PLANNED — запланировано или заказано; CONFIRMED — пользователь явно сообщил, что съел или выпил.
- Сообщение «заказал» не означает «съел».
- Подтверждение «съел» связывать с однозначно согласованным приёмом пищи; при неоднозначности уточнять.
- Не добавлять неподтверждённые продукты и не учитывать одно подтверждение дважды.
- В дневном итоге факта учитывать только CONFIRMED; прогноз с PLANNED показывать отдельно.
- Определять «сегодня» по настроенному часовому поясу пользователя. Не переносить вчерашний CLOSED-день в сегодняшний итог.
- После закрытия дня сохранять фактический итог; поздние уточнения обрабатывать как явную корректировку.

## Будущая синхронизация Airtable

Интеграция пока не реализована. При реализации:

1. Читать актуальные NutritionSyncProtocol и NutritionCalculationProtocol из Config; при недельном планировании — WeeklyPlanningProtocol.
2. Читать DailyState и Meals для нужной даты.
3. Обрабатывать новые подтверждения после LastUpdate с защитой от повторного учёта.
4. Сохранять раздельно факт и план; обновлять Version и LastUpdate по действующему протоколу.
5. Проверять результат чтением после записи и сообщать проверенную Version.
6. При ошибке честно сообщать о ней; не утверждать, что данные сохранены.
7. Не перезаписывать более свежие изменения без проверки версии.

## Проверки при реализации

- Расчёт продукта по массе и суммирование без накопления округлений.
- Замена запланированного блюда без двойного учёта.
- Заказ остаётся PLANNED до явного подтверждения.
- Повторное подтверждение не создаёт дубликат.
- Новый день не включает записи предыдущего.
- Ошибка записи не отображается как успешная синхронизация.
